# 학습 자료: 우리 LBM 솔버의 최적화·병렬화 — 원리, 논리, 적용 이유

대상: 이 솔버의 물리는 알지만 HPC 구현은 처음인 사람.
방식: 개념 → 우리 솔버의 실제 수치 → 우리가 내린 선택과 그 이유.
기준 케이스: HVAB D40 = 91.6M 셀, 5-레벨 MLG, RTX 4090 24GB.

---

# 1장. 출발점: GPU 메모리에서 LBM이 차지하는 공간

LBM의 상태는 분포함수 f 하나다. D3Q27이면 셀마다 27개의 float32:

```
f 배열 크기 = 91.6M 셀 × 27 방향 × 4 byte = 9.9 GB
```

여기에 rho/u(16B/셀), 경계조건 배열(17B/셀), SGS 버퍼(24B/셀)가 붙는다.
**GPU 한 장이 24GB**라는 사실이 이 문서의 모든 결정을 지배한다.

LBM 한 스텝 = collision(셀별 독립 계산) + streaming(이웃으로 값 이동).
두 성질이 이후 모든 것의 기반이다:
- collision은 **셀별 독립** → 셀들을 어떻게 나눠 계산해도 결과가 같다.
- streaming은 **순수 이동(치환)** → 숫자가 바뀌지 않고 위치만 바뀐다.

이 두 성질 덕분에 "재배열·분할을 아무리 해도 비트 하나 안 바뀌는" 구현이
가능하고, 우리는 그것을 검증 기준으로 삼았다(→ 6장).

# 2장. 단일 GPU 최적화 — 무엇을 왜 했나

## 2.1 Esoteric Pull: f 메모리 반감 (19.8 → 9.9 GB)

표준 구현은 streaming 때문에 버퍼가 2개 필요하다: 읽는 f와 쓰는 f_post.
같은 버퍼에 쓰면 아직 안 읽은 이웃 값을 덮어쓰기 때문이다.

Esoteric Pull(Lehmann 2022)은 버퍼 1개로 이것을 해결한다. 핵심 아이디어:
반대 방향 쌍 (i, i+1)의 두 population은 서로의 자리를 정확히 맞바꾸며
이동한다. 그래서 "슬롯"과 "방향"의 대응을 **홀수/짝수 스텝마다 뒤집으면**
(parity swap) 덮어쓰기 없이 제자리 갱신이 된다.

- 대가: 메모리 안의 f가 "물리적 f"가 아니다. 스텝 parity에 따라 슬롯이
  섞여 있어, 물리량이 필요할 때마다 변환(gather)이 필요하다.
- 우리가 얻은 것: **D40이 24GB 한 장에 들어감** (표준 경로는 ~25GB 필요).
  이것이 esoteric을 채택한 유일하고 충분한 이유였다.

## 2.2 커널 융합(fusion): 메모리 왕복 줄이기

GPU 연산의 비용은 대부분 산술이 아니라 **메모리 읽기/쓰기**다.
`a = b + c; d = a * e` 를 파이썬(CuPy) 연산 체인으로 쓰면 각 연산이
전체 배열을 램에서 읽고 다시 쓴다 — 2번의 왕복. 한 CUDA 커널 안에서
`d = (b + c) * e` 로 계산하면 1번의 왕복이다.

우리가 융합한 곳(각각 프로파일로 병목 확인 후):
- C2F rescale (patch 12): 시간보간+모멘트+평형+재구성 체인 → 커널 1개.
- `_feq_fneq`: 커플링의 평형/비평형 분해 → 커널 1개.
- ALM 샘플링 `alm_sample_markers`: 마커당 (N,S³) 중간배열을 만들던 체인
  → 마커당 1블록 커널. **step()의 85-90%를 차지하던 비용이 소멸**했다.

교훈: 융합 대상은 "짐작"이 아니라 **프로파일이 지목한 곳**이어야 한다.
우리는 coupling이 병목이라 짐작해 2번 헛수정을 했다(→ 5장).

## 2.3 Region gather/scatter 커널: 런치 폭풍 제거

esoteric ↔ 물리 f 변환을 영역 단위로 하는 함수가 halo/커플링/체크포인트
전부의 기반이다. 원래 구현은 방향쌍마다 fancy-indexing을 호출해
**호출당 커널 27개 + 인덱스 배열 13개**를 만들었다. 커널 하나 띄우는
데 ~5-10µs가 들고, GB급 블록에 이걸 45회/스텝 반복하니 D40에서
**스텝의 50%(5.2초 중 2.6초)** 가 여기 있었다.

단일 RawKernel(런치 1회, 인덱스는 커널 안에서 계산)로 교체 →
coupling 5.19 → 1.20 s/step. **순수 치환이므로 결과는 비트 동일**
— 이런 교체는 "공짜"다(정확도 손실 개념 자체가 없음).

## 2.4 결정성: 왜 연산 순서까지 통제하는가

부동소수점은 결합법칙이 성립하지 않는다: (a+b)+c ≠ a+(b+c) (마지막
비트에서). 라이브러리 리덕션(`xp.sum`, `einsum`→cuBLAS)은 **배열 크기와
GPU의 SM 수에 따라 더하는 순서를 바꾼다.** 같은 데이터라도 배열 모양이
다르면 결과가 1비트 다를 수 있다.

단일 GPU에서는 무해하다. 그러나 분산에서는 "rank의 작은 조각"과 "전체
배열"이 같은 값을 내야 하는데, 순서가 달라지면 비교 검증이 불가능해진다.
실제로 클러스터에서 가장 얇은 두 rank만 1비트 어긋난 사건이 있었고(§6),
해법은 **고정 순서 누적**(커널 안에서 q=0,1,2,... 순서로 직렬 합산)이었다.

규칙으로 남긴 것: **분산이 지나가는 경로에는 라이브러리 리덕션을 두지
않는다. 리덕션은 커널 안 고정 순서로.**

# 3장. 멀티 GPU: 도메인 분해의 실제

## 3.1 기본 그림

- **rank** = MPI 프로세스 1개 = GPU 1장.
- 도메인을 한 축(y)으로 썰어 rank마다 한 조각(**슬랩**)씩 준다.
- collision은 셀별 독립이라 각자 계산하면 되고, 문제는 streaming뿐이다:
  슬랩 경계 셀의 이웃이 **다른 GPU의 메모리**에 있다.

## 3.2 Ghost(halo): 경계 문제의 표준 해법

각 슬랩에 이웃 rank 소유 영역의 **복사본 층(ghost)** 을 몇 겹 붙인다.
매 스텝 전에 이웃과 경계 밴드를 교환해 ghost를 최신으로 만들면, 경계
셀도 로컬 메모리만 읽고 계산할 수 있다.

몇 겹이 필요한가? = **커널이 몇 칸 밖을 읽는가**로 결정된다:
- 순수 LBM: streaming 1칸 + "ghost 1층은 계산도 해줘야 소유 경계에
  올바른 값을 밀어넣는다" → 2겹.
- dyn_smag SGS는 속도 구배(반경 2)를 읽는다 → 3겹.
  일반 규칙: **ghost ≥ 1 + (커널의 비국소 입력 총 반경)**.
  (이 규칙은 게이트가 ghost=2로 SGS를 돌리다 소유 셀 오염을 잡아내면서 확립됐다.)

교환량은 작다: 면당 2-3층 × 27방향. D40 4-rank에서 halo는 스텝의
~15-20%이고, 그마저 대부분은 전송이 아니라 **이웃을 기다리는 시간**이다.

## 3.3 MLG 커플링은 왜 통신이 필요 없나

핵심 트릭: **fine 레벨의 컷을 coarse 컷에서 파생**시킨다
(fine 시작 = 2×(coarse 시작 − 박스 원점)). 그러면 레벨 간 보간(C2F/F2C)이
읽고 쓰는 영역이 rank 경계에서 정확히 맞아떨어져, 커플링은 각 rank가
자기 조각에서 **로컬로** 수행한다. 레벨 간 MPI 메시지는 0이다.

## 3.4 ALM: 회전 날개가 컷을 넘나드는 문제

마커의 속도 샘플링은 주변 셀들의 가우시안 가중합인데, 마커 스텐실이
rank 경계에 걸린다. 우리의 프로토콜:

1. 각 rank가 **자기 소유 셀만으로** 분자(Σw·u)와 분모(Σw)를 부분합.
   스텐실이 소유 경계에서 잘리므로 이중계산이 구조적으로 불가능.
2. 부분합을 Allreduce(전체합) — 마커당 4개 숫자, 전체 **~16KB**.
3. 나눗셈 후의 u_markers는 전 rank 동일 → BEM/보정 계산을 모든 rank가
   **똑같이 복제 수행**(통신 0). 결정적 계산이라 결과도 동일.
4. 힘 스프레딩은 각자 자기 슬랩에만.

"rank 0이 계산해서 뿌리기" 대안을 기각한 이유: 브로드캐스트 통신 +
코드 비대칭이 생기는데, 복제는 CPU 몇 ms로 그걸 다 없앤다.

## 3.5 컷을 어디에 둘 것인가: balance_cuts

균등 분할(240행을 4등분)은 **동작조차 안 한다**: MLG의 fine 박스들이
도메인 중앙에 몰려 있어, 바깥 rank는 L4 셀을 하나도 못 받는다(소유 0).

해법 한 줄: **모든 컷을 최내곽(L4) 박스 안에 둔다.** 박스들이 중첩
구조(L4⊂L3⊂...⊂L0)이므로 이 조건만으로 모든 rank가 모든 레벨을
소유하게 된다. 동시에 L3+L4가 계산량의 86%이므로, 계산량 밀도의
4분위점에 컷을 두면 부하 균형도 함께 얻는다(worst rank 26.6%, 이상 25%).

# 4장. 초기화: replicated build vs dist-init  ★질문의 핵심

## 4.1 "빌드"가 하는 일

시뮬레이션 시작 전에 만들어야 하는 것들:
- 격자/레벨 구조, 커플링 기하 (작음)
- **경계조건 배열**: 셀마다 "너는 유체/고체/입구/스펀지" 표시 + 목표
  rho/u 값 = 17 B/셀
- **초기 f**: 초기 rho, u로부터 평형분포 계산 = 108 B/셀
- rho/u/SGS 작업 버퍼 = 40 B/셀

production 빌더(SimulationSetup + SolverInitializer)는 이걸 전부
**전체 도메인 크기의 GPU 배열**로 만든다. 단일 GPU에서는 당연한 일이다.

## 4.2 방법 1 — replicated build (M5의 첫 구현)

멀티 GPU에서 가장 단순한 방법:

> 4개 rank가 **각자 자기 GPU에서 전체 케이스를 통째로 빌드**한 뒤,
> 자기 슬랩만 잘라 갖고(wrap-slice) 나머지를 전부 해제한다.

**왜 이렇게 했나 (장점):**
- 검증된 단일-GPU 빌드 코드를 **한 줄도 안 바꾸고** 재사용한다.
  빌드는 결정적이므로 4개 rank의 전체 상태가 비트 동일 — "내 슬랩"을
  자르면 자동으로 정합이 보장된다.
- 새 코드가 없으니 새 버그도 없다. M1~M3의 bit 검증이 이 단순성 위에
  세워졌다.

**대가 (단점):**
- 빌드 순간의 GPU 메모리 피크 = **전체 케이스 크기** (D40에서 19.2GB).
- 따라서 4장을 꽂아도 **케이스 크기 한도는 한 장짜리 그대로**(~110M 셀).
  GPU 4장 = 속도 4배이지 크기 4배가 아니게 된다.

"풀사이즈 배열을 만들면 뭐가 좋은가"의 답: 좋아서가 아니라 **기존 코드를
그대로 쓰는 가장 단순하고 안전한 길**이어서다. 우리는 언제나 "단순하고
증명 가능한 것 먼저, 필요가 실증되면 최적화"의 순서로 갔다.

## 4.3 방법 2 — dist-init ("rank가 자기 슬랩만 초기화")

450M 셀급이 목표가 되자 replicated의 대가가 실제 장벽이 됐다. 그래서:

> 빌드 때 큰 GPU 배열을 **아예 만들지 않고**, 각 rank가 자기 슬랩
> 크기만큼만 직접 생성한다.

가능한 이유 — 초기화 데이터가 전부 "좌표의 함수"라서:

1. **초기 f**: 우리 케이스의 초기조건은 균일(rho=1, u=상수)이다.
   균일하면 평형분포도 **모든 셀에서 같은 27개 숫자**다. 전체 배열을
   만들 이유가 없다 — 그 27개를 슬랩에 브로드캐스트하면 끝.
   (같은 함수로 계산하므로 replicated와 비트 동일 — 게이트로 증명.)
2. **경계조건 배열**: "x=0 면은 입구, x 끝 20층은 스펀지, 이 구 안은
   고체" — 전부 좌표 규칙이다. 같은 생성 함수를 **호스트(CPU RAM)**
   에서 전체 크기로 돌리고(17B/셀 — 450M이어도 7.7GB RAM, GPU와 달리
   싸다), 각 rank는 자기 슬랩만 GPU로 올린다.
3. rho/u/SGS 버퍼: 원래부터 슬랩 크기로 러너가 만든다.

**결과 (실측):** 빌드 피크 19.2 → **0.91 GB**. rank당 정착 3.7GB.
4×4090 수용량 **~110M → ~450-500M 셀**.

**대가:** 초기조건이 균일해야 한다(비균일 IC면 replicated로 — fail-fast
가 명시적으로 막는다). 재시작과 병용 불가(재시작은 전체 f를 복원해야
하므로 replicated 경로).

## 4.4 두 방법의 관계

| | replicated | dist-init |
|---|---|---|
| 철학 | 기존 코드 재사용, 단순성 | 필요해진 순간에만 추가한 최적화 |
| GPU 피크 | 전체 케이스(19.2GB) | 슬랩만(0.9GB 빌드) |
| 4-GPU 크기 한도 | 한 장과 동일 ~110M | ~450M |
| 제약 | 없음 (obstacle, 재시작 OK) | 균일 IC만, 재시작 불가 |
| 정확도 | 기준 | replicated와 **비트 동일** (게이트) |

이 순서(단순한 것 먼저 → 실측이 요구할 때 확장)가 우리 구현 철학의
표본이다. dist-init을 처음부터 만들었다면 M1~M3의 검증이 그만큼
늦어지고 복잡해졌을 것이다.

# 5장. 성능 작업의 방법론: 우리가 실제로 밟은 길

D40 4-rank 첫 실측은 0.671...이 아니라 **3.24 s/step — 단일과 같았다**
(가속 0). 이후의 과정이 성능 작업의 교과서적 실패와 회복이라 기록한다.

1. **어트리뷰션 먼저**: --profile로 스텝을 섹션별로 쪼갬 →
   coupling 1.0 / halo 1.5 / alm 0.34 / **kernel 0.10** — LBM 계산은
   3%뿐, 나머지는 전부 오케스트레이션이었다.
2. **추측 수정 2연속 실패**: "coupling이면 모멘트 체인이겠지"(수정→
   −0.07s), "그럼 upsample이겠지"(수정→0) — 프로파일은 섹션까지만
   알려주지 섹션 안의 범인은 알려주지 않는다.
3. **재현 루프를 손에 넣음**: 클러스터 왕복 대신 로컬 1-GPU에서 같은
   코드를 도는 NR=1 모드를 만들어 **분 단위로 가설 검증**이 가능해짐.
   즉시 진범 발견(2.3절의 fancy-index 폭풍) → 5.19→1.20.
4. **정직한 재기준**: 최적화가 단일 GPU 경로도 같이 빨라지게 했으므로
   "4.6× 가속" 주장을 **동일 코드 기준 1.6~1.8×로 정정**. 이후 ALM
   커널화·halo 스케줄링으로 최종 0.442 s/step — 병렬화된 부분의 분할
   효율 ~100%(kernel 0.417→0.103×4).

남긴 규칙:
- 성능 주장에는 **비교 기준(코드 세대)을 명시**한다.
- 병목은 측정으로만 지목한다. 두 번 틀리면 **재현 루프부터 만든다**.
- 메모리 검증은 하드리밋 에뮬레이션으로 한다(`pool.set_limit`).
  WSL2는 GPU 메모리를 초과 할당해줘서 OOM을 숨긴다 — 이걸로 두 번 속았다.

# 6장. 검증 체계: bit-parity 사다리

병렬화 검증의 통상 관행은 "결과가 허용오차 안에서 같다"이다. 우리는
1장의 성질(collision=셀별 독립, streaming=치환) 덕분에 더 강한 기준을
세울 수 있었다:

| 등급 | 기준 | 어떤 연산이 이 등급인가 |
|---|---|---|
| **bit** | 비트열 완전 동일 | 치환(gather/scatter), 셀별 커널, halo, 커플링 |
| last-bit | ~1 ulp | 합산 순서가 바뀌는 곳 (ALM 부분합+Allreduce) |
| CV-band | 통계적 일치 | 난류 카오스 아래의 긴 궤적 비교 |

원칙: **연산마다 "어느 등급이어야 하는지"를 미리 논증하고, 예측과
다르면 등급 안이라도 원인을 찾는다.** 이 원칙이 잡아낸 실결함이 9건이다
(esoteric 초기화 롤 누락, SGS ghost 깊이, 균등분할 불능, shape-의존
리덕션, 연산자 미공유, 재시작 로터 위상 리셋, verify 진입점 파손,
NR=1 메모리 이중보유, solid 셀 미초기화 통계). 이 중 3건은 tolerance
검증이었다면 **조용히 물리를 오염**시켰을 것들이다.

가장 인상적인 결과: 최종 수용시험에서 단일 GPU와 3-rank가 2회전
(4만 substep) 동안 **모든 필드·마커·추력이 비트 단위로 동일**했다.
분산이 물리를 바꾸지 않는가에 대한 답을 오차가 아니라 0으로 낸 것이다.

# 7장. 용어집

- **rank**: MPI 프로세스. 우리 구조에서 GPU 1장 = rank 1개.
- **슬랩(slab)**: 도메인을 한 축으로 썰었을 때 rank 하나가 소유하는 조각.
- **ghost / halo**: 이웃 rank 소유 영역의 로컬 복사본 층 / 그것을 매
  스텝 갱신하는 교환.
- **parity**: esoteric의 홀·짝 스텝 슬롯 배치. 재시작 시 이어받아야 함.
- **gather / scatter**: esoteric 메모리 ↔ 물리 배열 순서 변환(치환).
- **Allreduce**: 모든 rank의 값을 합쳐 모든 rank에 돌려주는 MPI 집합연산.
- **커널 런치 오버헤드**: GPU 커널 하나 시작에 드는 ~5-10µs. 작은 커널을
  수천 번 띄우면 이것만으로 초 단위가 된다.
- **coalescing**: 인접 스레드가 인접 메모리를 읽도록 하는 배치. 어긋나면
  대역폭이 수 배 손실 (cubic-z 커널이 이 문제였다).
- **FMA / 결합순서**: 부동소수점 덧셈은 순서에 따라 마지막 비트가 달라짐.
  결정성 요구 지점에서는 순서를 고정해야 한다.
- **메모리 풀 / 파편화**: CuPy는 GPU 메모리를 풀로 관리한다. 큰 할당·해제가
  반복되면 총량은 남아도 연속 블록이 없어 할당이 실패할 수 있다.
- **replicated build / dist-init**: 4.2 / 4.3절.
- **MEM force**: 고체 표면에서 튕기는 population의 운동량 교환으로 힘을
  적분하는 방법 (CD/CL의 원천).
